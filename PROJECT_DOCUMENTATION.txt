1. PROJECT OVERVIEW
================================================================================

Documind is an enterprise-grade, AI-powered document intelligence platform that
automates the extraction, classification, validation, and analysis of business
documents such as invoices, receipts, contracts, and bank statements.

The platform processes uploaded documents through a multi-stage pipeline:

    Upload -> OCR -> OCR Correction -> Classification -> Field Extraction
    -> Validation -> Duplicate Detection -> Anomaly Detection -> AI Analysis
    -> RAG Indexing -> PDF Report Generation

KEY CAPABILITIES:
- Optical Character Recognition (OCR) using Tesseract
- LLM-powered OCR post-processing correction
- Machine Learning document classification (TF-IDF + SGD)
- Deterministic regex-based field extraction
- Business rule validation engine (6 rules)
- TF-IDF cosine similarity duplicate detection
- Isolation Forest anomaly detection
- Groq LLM semantic analysis (summaries, entities, risk)
- RAG (Retrieval-Augmented Generation) document Q&A
- Document comparison with field-level diffs
- Confidence scoring with weighted aggregation
- Branded PDF report generation
- Multi-document batch processing
- Docker containerization

    ML ALGORITHM & MODEL ARCHITECTURE
────────────────────────────────────────────────────────────────────

    MODEL TYPE: TF-IDF + Logistic Regression (scikit-learn)

    FEATURE EXTRACTION — TF-IDF Vectorizer:
        Algorithm:          Term Frequency-Inverse Document Frequency
        N-gram Range:       (1, 2) — unigrams and bigrams
        Max Features:       10,000 (vocabulary cap)
        Sublinear TF:       Enabled (applies log normalization)
        Stop Words:         None (financial terms may be stop words)
        Analyzer:           Word-level tokenization
        Output:             Sparse matrix of shape (n_docs, 10000)

    CLASSIFIER — Logistic Regression:
        Algorithm:          One-vs-Rest Logistic Regression
        Regularization:     L2 (Ridge)
        Solver:             lbfgs
        Max Iterations:     1000
        Multi-class:        One-vs-Rest (OvR)
        Output:             Probability distribution over 13 classes

    MULTI-TIER CLASSIFICATION ARCHITECTURE:
    1. Tier 1 — Classical Supervised ML (TF-IDF + Logistic Regression):
       - Converts cleaned OCR text into n-grams (1-2) with TF-IDF.
       - Returns probability scores. If confidence >= 0.50, adopts prediction.
    2. Tier 2 — Financial Heuristic Classifier (heuristics.py):
       - Trigger regexes (3.0 weight) + keyword vocabulary (1.0 weight).
       - Provides 70%-85% calibrated confidence when ML model is ambiguous.
    3. Tier 3 — AI Semantic Arbitration (Groq LLaMA-3.3-70B):
       - Validates document context and updates prediction if needed.

PHASE 6 — BUSINESS RULE VALIDATION
────────────────────────────────────────────────────────────────────

OBJECTIVE:
    Validate extracted fields against business rules to catch errors,
    inconsistencies, and compliance issues.

VALIDATION RULES (6):
    1. Mandatory Field Check
       - Ensures required fields are present (e.g., total_amount, date)

    2. Date Validity Check
       - Dates are valid and not in the future
       - Due date is after invoice date

    3. Arithmetic Consistency
       - Subtotal + Tax = Total Amount (within tolerance)

    4. Amount Range Check
       - Amounts are positive and within reasonable bounds

    5. Invoice Number Format
       - Matches expected patterns (alphanumeric)

    6. Cross-Field Consistency
       - Vendor name present if vendor address exists
       - Currency consistency across fields

VALIDATION STATUSES:
    - VALID:   All rules passed
    - WARNING: Non-critical rules failed
    - INVALID: Critical rules failed

────────────────────────────────────────────────────────────────────
PHASE 7 — DUPLICATE DETECTION
────────────────────────────────────────────────────────────────────

OBJECTIVE:
    Detect duplicate or near-duplicate documents using text similarity
    and content hashing.

DETECTION METHODS:
    1. SHA-256 Hash Match (exact duplicate)
       - Hash of cleaned text content
       - Similarity = 1.0 if match

    2. TF-IDF Cosine Similarity (near duplicate)
       - Build TF-IDF vectors from all document texts
       - Compute pairwise cosine similarity
       - Flag pairs above threshold (default: 0.85)

DUPLICATE TYPES:
    - EXACT:    SHA-256 hash match
    - NEAR:     Cosine similarity >= 0.85
    - PARTIAL:  Cosine similarity >= 0.70

PHASE 8 — ANOMALY DETECTION
────────────────────────────────────────────────────────────────────

OBJECTIVE:
    Detect statistically anomalous documents using an Isolation Forest
    model trained on document feature vectors.

FEATURES USED:
    - Text length (character count)
    - Word count
    - Number of extracted fields
    - Total monetary amount
    - Number of validation failures
    - Classification confidence

TRAINING:
    - Unsupervised (no labels required)
    - Contamination factor: 0.05 (5% expected anomalies)
    - Auto-trains when >= 5 documents exist

OUTPUT:
    - is_anomaly: boolean flag
    - anomaly_score: float (higher = more anomalous)
    - decision_function_score: float (negative = anomaly)

PHASE 12 — RAG-BASED DOCUMENT Q&A
────────────────────────────────────────────────────────────────────

OBJECTIVE:
    Allow users to ask natural language questions about uploaded
    documents using a Retrieval-Augmented Generation (RAG) pipeline.

RAG ARCHITECTURE:
    User Question
      |
      v
    Question Embedding (all-MiniLM-L6-v2)
      |
      v
    Vector Similarity Search (cosine, top-5 chunks)
      |
      v
    Context Construction (relevant chunks + metadata)
      |
      v
    Groq LLM (grounded answer generation)
      |
      v
    Answer + Source Citations

DOCUMENT INDEXING:
    - Documents split into page-aware chunks (500 chars, 100 overlap)
    - Each chunk retains: document_id, page_number, chunk_id, source text
    - Chunks embedded using sentence-transformers
    - Stored in in-memory vector store (NumPy cosine similarity)

Q&A MODES:
    1. Single Document Q&A
       - POST /api/documents/{id}/qa
       - Searches only within the specified document

    2. Multi-Document Q&A
       - POST /api/documents/qa
       - Searches across all indexed documents
       - Returns answers with document source citations

FRONTEND:
    - Chat-style interface with message bubbles
    - Document selector dropdown
    - Source citations with page numbers and match scores
    - "Ask across all documents" mode

6. DATABASE SCHEMA
================================================================================

TABLE: documents
    document_id              UUID PRIMARY KEY
    filename                 VARCHAR(255) NOT NULL
    original_filename        VARCHAR(255)
    file_type                VARCHAR(50) NOT NULL
    file_size                INTEGER NOT NULL
    file_path                VARCHAR(512) NOT NULL
    status                   ENUM (uploaded, processing, completed, failed)
    document_type            VARCHAR(100)
    classification_confidence FLOAT
    classified_at            TIMESTAMP
    created_at               TIMESTAMP DEFAULT NOW()
    updated_at               TIMESTAMP

TABLE: document_contents
    id                       SERIAL PRIMARY KEY
    document_id              UUID FK -> documents
    page_number              INTEGER NOT NULL
    raw_text                 TEXT
    cleaned_text             TEXT
    created_at               TIMESTAMP DEFAULT NOW()

TABLE: extraction_results
    id                       SERIAL PRIMARY KEY
    document_id              UUID FK -> documents (UNIQUE)
    extracted_fields         JSONB
    extracted_at             TIMESTAMP DEFAULT NOW()

TABLE: validation_results
    id                       SERIAL PRIMARY KEY
    document_id              UUID FK -> documents (UNIQUE)
    status                   VARCHAR(20)
    rule_results             JSONB
    validated_at             TIMESTAMP DEFAULT NOW()

TABLE: anomaly_results
    id                       SERIAL PRIMARY KEY
    document_id              UUID FK -> documents (UNIQUE)
    is_anomaly               BOOLEAN
    anomaly_score            FLOAT
    decision_function_score  FLOAT
    feature_vector           JSONB
    created_at               TIMESTAMP DEFAULT NOW()

TABLE: duplicate_results
    id                       SERIAL PRIMARY KEY
    document_id              UUID FK -> documents
    matched_document_id      UUID
    similarity_score         FLOAT
    duplicate_type           VARCHAR(20) (EXACT, NEAR, PARTIAL)
    created_at               TIMESTAMP DEFAULT NOW()
